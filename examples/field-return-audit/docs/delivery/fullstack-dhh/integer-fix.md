# SQLite 整数精确证据返修

父验收记录编号 `9007199254740993` 在浏览器变成 `9007199254740992`。后端原本保留 Python 整数，问题发生于浏览器将 JSON 数字读入普通数值。本次在数据库值进入证据结果时编码，并保留现有档案工作台的布局、颜色和交互。

| 位置 | 本次行为 |
| --- | --- |
| 所有 SQLite INTEGER 值 | `{"type":"integer","value":"9007199254740993"}`；小整数、非键字段及正负 64 位端点使用同一协议 |
| 同字符 TEXT | 保持 JSON 字符串 `"9007199254740993"`，与整数身份不同 |
| 记录键与复合键 | 每个键值分别保留存储类型与原值；内部按类型和原值索引 |
| 字段变更 | 按存储类型与原值比较，整数 `1` 与实数 `1.0` 的类型变化也列为差异 |
| 显式关联规则 | 父、子字段存储类型必须一致，再比较原值；数据库原生外键仍按 SQLite 约束检查 |
| 原生外键问题 | 定位用 `rowid` 编码为精确整数；约束序号保留元数据数值 |
| 界面、CSV、独立 HTML | 单字段整数显示为 `整数 · 原值`，同字符文本显示为 `文本 · "原值"`；记录键保留含类型标签的 JSON |
| 中文 JSON 导出 | 标签 `type`、`integer`、`value` 是固定协议标识，保留原样；数据库字段名及文本不改写 |
| 计数与文件证据 | 记录数、字节数及哈希描述仍使用原有安全元数据；BLOB 描述重复编码保留字节计数 |

实现集中在 `audit.py` 与 `app.js`。`server.py` 继续使用现有 JSON 序列化，业务整数已成为有类型的字符串描述，无需在 HTTP 层猜测或补救舍入。没有新增依赖、外部请求或数据写入。

这是证据数据协议的明确变更：读取结果的其他本地程序应使用 `type` 区分整数，并将 `value` 交给可精确解析十进制整数的类型，不能转换为浏览器普通数值。SQLite 已经按照字段亲和性存储的内容以实际读取类型为准，工具不能还原入库前丢失的类型或精度。

本角色未运行正式测试；独立 QA 补充边界、关联、HTTP 和真实浏览器导出回归，由协调器通过原交付运行器统一执行并保留结果。正式检查前的本记录只说明实现，不宣称验收通过。
